## 1. The goal, stated so it can fail

A person who has never made a skin installs FM Skin Studio, and within ten minutes, without opening a document, has a recoloured skin showing in the game. Today that person stops at one of the points in section 2.

Acceptance is a scripted first-run test (section 9), with the clock defined in advance. It is not "the views exist".

**Results (one machine, the owner's PC):**
- **Tokens.** 2,059 tokens, 49 sheets: the same totals as the two-build diff baseline in `docs/PHASE5-EVIDENCE.md` (2059 / 49), an independent consistency check of the index. 1,481 are colour tokens in 139 families; **740 are used by at least one rule and 741 by none** ("none" means no decoded USS rule references them with `var()`; game code could still read them, which this index cannot see). 11 colour tokens have different values in different sheets.
- **Crimson, token level.** It overrides 422 tokens, 418 of them colour tokens. **188 of those 418 are tokens no rule uses**; the other 230 are 31% of the 740 used colour tokens and reach 4,340 of the 10,687 rule paths the used tokens reach (41%). So "Crimson-like coverage" is about 230 used tokens and 41% of the rule reach; 100% is not the target.
- **Crimson, role and ramp level (the second source for S4's role map).** For each of the 418 overrides the file records the ramp and step Crimson gave it (the output colour matched against the preset's own palette, read from the preset's code, not retyped), the preset's own note (a design-guide section and the rule applied, such as "vanilla -40 -> Light" or "10-step linear scale") and the inferred role. By ramp: 301 land on a palette entry (crimson 62, neutral 30, text 20, alpha overlays 8, the eleven hue families 139 in all, the data scale 22 and its dark tints 20) and **117 are computed at the token** (off the palette). By role: base hue ramps 125, chart / data series 107, tactics position 34, accent 31, brand palette 31, calendar / training 17, hover / pressed 12, coaching rating 10, border / divider 9, accent text 6, primary text 6, raised surface 6, status / club marker 6, UI surface ramp 4, warning / notice 3, and 1 to 2 each for page background, secondary text, selection, positive, negative, focus ring; none unclassified. **The roles are INFERRED from token names by ordered rules (`ROLE_RULES` in the tool, each row records the rule that fired); the ramp, step and note are the preset's own data.** What this means for S4: the roles the user's three colours drive directly (page background, raised surface, accent, text, hover, selection, borders) are few tokens each; most of Crimson's 418 are hue ramps, chart colours and position colours, which a three-colour input cannot derive from "background, accent, text" without a rule (S4 decides which of them to leave at the game's colours).
- **Literals (amendment B).** 956 distinct literal colours (RGB + alpha) in the game's rules; **449 have at least one use** (2,529 uses in all; 2,127 of them on colour properties) and 507 occur only inside token definitions (the token route covers those). Per literal the file holds uses, distinct selectors, rule paths, sheets, top properties and the number of game rules a native export copies for each swap mode. The distribution: a swap in exact-alpha mode copies 1 to 5 rules for 354 of the 449, 6 to 20 for 76, 21 to 50 for 15 and more than 50 for 4; in keep-alpha mode (the mode Crimson uses) it copies 1 to 5 for 236, 6 to 20 for 124, 21 to 50 for 35 and **more than 50 for 54**. The heaviest are `#000000` at alpha 0 (253 uses, 98 selectors, 5 sheets), `#FFFFFF` (147 uses, 96 selectors) and `#FFFFFF` at alpha 0 (82). Crimson's 70 swaps copy 462 game rules (checked by the tool against `native.literal_rules`: the index-based count and the native export's own count agree), 18% of all literal uses. **Meaning for S3:** a literal change is cheap and local for most colours (the median colour has 2 uses) and a heavy rewrite for a few (the 54 colours above 50 copied rules); the panel shows the count before applying, as amended, and the click offers a literal only below a stated limit (to be set from this distribution in S3, proposed 50 copied rules, with the heavy ones pointing to Advanced).

### S3. Click it, recolour it
In Simple mode the render becomes pickable: click an element, get a small panel with the colours it shows, each with a picker.
- A colour from a token changes a token override. Before applying, the panel states how many other elements in this layout use the token and **how many of the 8 modelled screens (club, competition, portal, recruitment, squad, tactics, tactics-instructions, training) change with it**, from the shipped models, not from a layout dump (section 0, #13).
- **Limit approved (owner, 2026-11-15): 50 copied rules.** Above it the panel says "This colour is used in many places; changing it here is an Advanced job", with the count shown. **The panel never offers a swap that copies nothing:** Crimson's own 70 literal swaps include 22 that hit 0 rules (S0), so a literal with 0 copied rules is not offered, and neither is a swap whose only uses are token definitions (the token route covers those). The counts come from `data/simple/token-inventory.json` (uses, selectors, rule paths, copied rules per mode).
- **Count source, checked offline 2026-11-15 (S3 preparation):** the 'of the 8 modelled screens' figure CAN be produced without a layout dump, from the shipped models through `preview.evaluate` (regions measured on the eight screens), not through `where.token`. **It undercounts, and S3 must word it so:** with a probe project that changes one token to red, `--colours-ui-deep` changes a region on 8 of the 8 screens, `--global-text-primary` on 8 of 8 (hundreds of regions each), `--layout-surfaces-cards-surface` on 5 of 8, while `--global-background` and `--brand-theme-primary` change 0 of 8 even though they plainly paint the game (the models hold only the regions that were measured, and those two reach the screen through areas they do not hold). So "0 of the 8 measured screens" must never read as "nothing changes": the wording is "N of the 8 measured screens show this colour in an area we measured", with 0 shown as "not in an area we measured". **DECIDED (owner, 2026-11-15): the model-based count is used as it is.** A token reads "used on N of the 8 measured screens we have models for"; where the count is 0 it reads "not used on the 8 screens we have models for; it may still change screens we have not measured". Never "nothing changes". No `where.token` and no layout dump anywhere in Simple mode.
- A colour that is a literal in a game rule is offered through `literal_swaps` only if S0 shows it is safe from a click. In a native skin a literal change COPIES every game rule that uses the literal, so the panel shows the copied-rule count before applying, beside the use count and the selector count. Otherwise it says "this colour is fixed in the game" and points to Advanced. No scoped rule is written by a click in this version.
- **'My colours' (owner requirement, 2026-11-15):** the user can save up to 10 colours as a personal palette. **Wherever a colour is picked in Simple mode (the Colours view's swatches and the click-to-recolour panel below), the palette appears as one-click choices beside the raw picker.** Adding and removing entries is explicit (a star saves the colour in front of you, an Add button saves one you pick, a cross removes one; using a colour never adds it). **'Put back' is unchanged: it always returns to the game's own colour,** never to a previous pick. A saved colour is plain #RRGGBB: applying it keeps the transparency of the colour it replaces. Kept in the browser's storage on this PC, like the window size (`studio/src/myColours.ts`). **Built now for the Colours view** (`Palette.tsx`: a My colours section with its count, a star and a choices button on every row, and the same two controls on the top-bar colour; 5 tests in `Palette.test.tsx`); **S3's click-to-recolour panel reuses the same strip component** when it is built. I see no reason to move it to another milestone: the Colours view needed it now and the panel only adds the second place; S5 is not reordered.
- A colour the render cannot attribute (run-time club colours, code-drawn visuals: the known gaps of the calibration report) is shown as such: "the game paints this while running; it can't be changed here".
- "Put it back" on every change.
Uses the render's existing origin data; adds no render rule (the two-source rule is not engaged); inherits every limit of the render.

### S4. A theme from three colours
The user picks a background, an accent and a text colour (and dark or light); the Studio writes the token overrides for the whole palette.
- A **role map** (`data/simple/roles.json`) assigns tokens to roles; ramps between the inputs are computed the way the Crimson preset computes its own.
- **Scope of the map (S0 data):** the role map covers only the 740 colour tokens some rule uses; the 741 unused ones stay unmapped and invisible in Simple mode. **Three inputs, several hundred derived values:** the user gives a background, an accent and a text colour (and dark or light); the map derives the ramps; the target is Crimson-like coverage (about 230 used tokens, 41% of the rule reach), not 100%.
- **Every role-map entry is marked `unverified` until the in-game check (amended).** Both sources (the Crimson preset and the token's usage in the game's rules) are inferences, and Crimson's own native form has not been looked at in the game yet (Session 1 (a)). An entry has no other status in this plan; the gallery says "not yet checked in the game" for every theme until Session 2 has recorded it.
- **Checks, automated:** every token in the map exists in the style index of the current build; the export of a generated theme writes more than zero tokens; **contrast (ratio 4.5) is checked on EVERY theme generated from the user's own colours, at the moment of generation, and fails loudly** (the generate button reports the failing pairs and does not write the theme) (amended; not only on the gallery). The project model already has `contrast_pairs`.
- A small **gallery** of themes generated by the same code (not hand-made files), plus Crimson as it is.

## 7. Risks
1. **The role map is wrong in places the offline render cannot show** (run-time or code-drawn surfaces). Mitigation: every entry `unverified`; the in-game gate before any theme is called working; Crimson as the base only after Session 1 (a). Not mitigated: a later game update that renames tokens (the update diff and the map's existence check will show it).
2. **The approximation misleads a beginner more than an expert.** Mitigation: before / after of two offline renders, the notice kept, "the game paints this while running" where the render cannot attribute a colour, no quality number restated in Simple mode.
3. **Simple and Advanced edit the same project.** A project broken in Advanced locks Simple mode out until fixed; the plain message points to Advanced; no automatic repair.
4. **The Preferences step cannot be removed or checked offline.** One step, once per skin name; a fixed skin name per project; clear wording; a failure there is recorded as a finding.
5. **First-run setup is the biggest unknown** (S1a): it reads the game's bundles, takes a snapshot of them and decodes every stylesheet. Its time and failure modes on a clean machine are unmeasured; the section 9 clock records it as its own component.
6. **Scope.** Ten milestones; the split in section 6 is the mitigation.
